## 4.3.1

Initial release. The package installs Kata Containers 4.3.1's `qemu-nvidia-cpu-runtime-rs`,
registered with containerd as `kata-qemu-nvidia-cpu-runtime-rs` and exposed through the
`kata-containers-qemu-nvidia-cpu-runtime-rs` RuntimeClass. It runs Kata's own finite
installer stages under NodeWright's rollout, drain and lifecycle controls, so there is no
kata-deploy DaemonSet and no agent image override. It is CPU only: GPU Operator, NFD and
the Kata device plugins are not dependencies. Standalone containerd, K3s, RKE2, MicroK8s
and k0s are discovered automatically.

The package version is the Kata version; there is no separate adapter version. The build
fails when `package_version` in `config.json` does not match the pinned Kata image, so
each new Kata release ships as a new package version.

### Host requirements

- containerd >= 2.3 and `erofs-utils` >= 1.8.2, both required by the EROFS memory and
  dm-verity profile. The package rejects an older containerd before it touches CRI
  configuration, and it never upgrades either one on the host.
- Stock Ubuntu 24.04 ships `erofs-utils` 1.7.1, which is too old. Ubuntu 26.04 is the
  validated path.
- MicroK8s 1.36.2 cannot run this profile: its snap bundles containerd 2.2.3 and
  `erofs-utils` 1.4, and a newer `erofs-utils` on the host does not replace the snap's copy.
- On K3s and RKE2, the generated containerd config must already import the
  `config.toml.d` or `config-v3.toml.d` drop-in directory; Kata refuses to install
  otherwise rather than rewrite the distribution's config.
- About 110 MiB of free disk for the staged installer (roughly 106 MiB on amd64, 108 MiB
  on arm64). Successful post-interrupt and uninstall stages remove it; a failed stage
  keeps it for diagnosis.

### Before you apply it

- Apply `smoke-rbac.yaml` with the RuntimeClass and NodeWright manifests. Before a node
  completes, post-interrupt boots a Kata pod on that node and blocks completion, keeping
  the runtime-required taint, until the guest runs and the pod is deleted. The check uses
  a dedicated service account limited to the `kata-containers-smoke` namespace. If the
  operator does not run in the `nodewright` namespace, edit the subject namespaces in that
  file.
- Taint existing nodes with the runtime-required taint
  (`nodewright.nvidia.com=runtime-required:NoSchedule` by default) before adding them to the
  group, and have future pool nodes join with it. `autoTaintNewNodes` is enabled, but it is
  a fallback with a scheduling race and does not re-taint nodes NodeWright already handled.
- On a single-node cluster, give the operator's pods tolerations for
  `node.kubernetes.io/unschedulable:NoSchedule` and the runtime-required taint, so the
  controller keeps running while NodeWright drains its node.

### Validation coverage

End-to-end testing covered Ubuntu 26.04 arm64 VMs with nested KVM only: kubeadm with
standalone containerd, K3s, RKE2 and k0s. The automated post-interrupt smoke gate was
exercised through NodeWright on K3s only. amd64 guest execution, bare metal, DPU hardware
and SELinux-enabled hosts have not been tested.

Apple silicon nested virtualization (for example Lima VMs) also needed the runtime
overrides `cpu_features = ""` and
`machine_accelerators = "usb=off,gic-version=host,its=off"`, set through the
`dropin-qemu-nvidia-cpu-runtime-rs.toml` ConfigMap key.
